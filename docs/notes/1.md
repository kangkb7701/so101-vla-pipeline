# OpenVLA 물리적 실행 안정성 개선 보고서 (Genesis 엔진)

본 문서는 OpenVLA의 의도를 Genesis 시뮬레이션 환경에서 실제로 구동하기 위해 적용된 수치적, 시간적 보정 사항들을 분석합니다.

---

## 1. 주요 수정 사항 분석 (실행 안정성 관점)

### 1.1. 데이터 타입 통합 (Tensor to Numpy)
*   **문제**: Genesis 엔진은 내부적으로 CUDA Tensor를 사용하는 반면, OpenVLA의 출력과 좌표 계산은 Numpy 배열을 사용합니다. 이들 사이의 직접적인 연산은 `RuntimeError`를 발생시킵니다.
*   **수정**: `ee_link.get_pos().cpu().numpy()`와 같이 Genesis의 출력을 명시적으로 CPU Numpy로 변환한 뒤 연산을 수행하도록 통일했습니다.
*   **효과**: 연산 시 발생하는 데이터 타입 불일치 에러를 원천적으로 차단하여 스크립트의 실행 지속성을 확보했습니다.

### 1.2. 물리 엔진 서브스태핑 (Sub-stepping)
*   **문제**: 물리 엔진 스텝(`scene.step()`)이 제어 명령당 1회만 호출되면, 로봇이 목표 위치로 이동할 수 있는 물리적 시간(0.01초)이 부족하여 제자리에서 떨리는 현상(Jittering)이 발생합니다.
*   **수정**: 제어 명령 하달 후 `for _ in range(30): scene.step()` 루프를 도입하여, 로봇 모터가 목표 각도에 충분히 도달할 수 있는 물리적 시간을 확보했습니다.
*   **효과**: AI가 "앞으로 가"라고 했을 때 로봇이 실제로 그 지점까지 움직이는 것을 눈으로 확인할 수 있게 되었습니다.

### 1.3. 시점 정합 및 Pitch 보정
*   **문제**: 카메라가 내려다보고 있을 때(Pitching), AI의 "직진" 명령이 로봇 베이스 기준으로는 바닥을 찍어 누르는 대각선 궤적을 만들게 됩니다.
*   **수정**: 카메라 위치를 로봇 뒤쪽 상단으로 고정하고, `R_cam_to_base`의 역할을 명확히 정의했습니다. 1차 테스트 결과에 따라 이 행렬에 Pitch 회전의 역행렬을 곱해 "시각적 수평"을 "물리적 수평"으로 일치시킬 수 있는 구조를 마련했습니다.

## 2. 비판적 검토 및 향후 고도화 방향

### 2.1. 동기식 루프의 한계
*   **현상**: 현재는 VLA가 사진을 찍고 명령을 내릴 때까지 시뮬레이션 시간이 멈춰 있거나(Sub-stepping 도중 대기), 매우 비효율적인 루프 구조를 가집니다.
*   **한계**: 이는 실제 로봇의 실시간 제어(100Hz 이상)와는 거리가 멉니다.
*   **대안**: `Genesis`의 비동기 제어 기능을 활용하여, 추론은 백그라운드에서 돌고 제어는 고속으로 유지되는 구조로의 전환이 필요합니다.

### 2.2. IK 수렴 실패 대응
*   **현상**: `inverse_kinematics`가 불가능한 목표 지점을 받았을 때의 예외 처리가 부족합니다.
*   **한계**: 로봇이 특이점(Singularity)에 도달하면 팔이 갑자기 꼬일 수 있습니다.
*   **대안**: IK 계산 결과의 연속성을 체크하여 급격한 관절값 변화 시 해당 명령을 무시하거나 완화하는 필터 도입이 권장됩니다.

### 2.3. 그리퍼 물리성 확보
*   **현상**: 그리퍼를 단순히 위치 제어(`control_dofs_position`)로 움직이고 있습니다.
*   **한계**: 물체를 잡았을 때 발생하는 압력이나 마찰력이 부족해 물체가 빠질 수 있습니다.
*   **대안**: 잡기 동작 시에는 힘 제어(Force/Torque) 모드로 전환하여 큐브를 으깨지 않으면서도 단단히 잡을 수 있는 로직이 필요합니다.
