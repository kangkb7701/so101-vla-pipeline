# 연구 프로젝트 및 시스템 아키텍처 피드백

`정리.md`와 현재 코드(`vla_sim.py`), 그리고 리뷰 문서들을 검토한 결과, 본 프로젝트는 매우 실용적이면서도 학술적인 가치가 높은 방향으로 설정되어 있습니다. 질문하신 두 가지 사항에 대해 제 생각을 정리해 드립니다.

---

## 1. 연구 논문으로서의 가치 및 차별성 (Q1)

**결론부터 말씀드리면, "충분히 의미 있고 매력적인 주제"입니다.**

최근 로보틱스 연구의 흐름은 거대 모델(VLA)을 어떻게 실제 환경, 특히 **제한된 자원(Low-cost hardware, Personal GPU)**에서 효율적으로 구동하느냐에 집중되어 있습니다. 본 연구가 가질 수 있는 차별점은 다음과 같습니다.

*   **민주화(Democratization)된 로봇 연구**: 수억 원대 하이엔드 로봇(PR2, Panda 등)이 아닌 저가형 하드웨어(SO-ARM100 등)와 개인용 GPU 환경을 타겟으로 한 End-to-End 제어 제안은 현업 개발자와 독립 연구자들에게 매우 높은 실용적 가치를 가집니다.
*   **지연 시간(Latency) 중심의 실증 분석**: VLA 모델은 추론 속도가 느린 것이 고질적인 문제입니다. 단순히 "된다"를 넘어, "지연 시간이 발생할 때 제어 알고리즘(IK vs RoLA vs ACT 등)이 어떻게 반응하고 성공률이 변하는가"를 정량적으로 분석하는 것은 매우 훌륭한 논문 주제입니다.
*   **현실적인 시스템 아키텍처**: 시스템 구상도에서 제안하신 'VLA -> IK/RoLA -> Simulation/Real' 흐름은 최신 'Foundation Model for Robotics'의 표준 파이프라인을 잘 따르고 있습니다.

**[논문 고도화를 위한 제언]**
*   **"Efficiency-Performance Trade-off"**를 핵심 키워드로 잡으세요. 모델의 크기나 제어 방식에 따른 성능 변화를 비교하면 논문의 논리가 탄탄해집니다.

## 2. 모듈화 전략: "레고 블록" 아키텍처 제안 (Q2)

논문 실험을 위해 모델(VLA)이나 제어 방식(IK, RoLA, ACT)을 쉽게 교체하려면, 현재의 단일 스크립트 구조를 **기능 단위로 분리(Decoupling)**해야 합니다.

### 권장 프로젝트 구조

```text
project_root/
├── agents/             # "Brain" 역할 (모델 관리)
│   ├── base_agent.py   # 추상 인터페이스
│   ├── vla_agent.py    # OpenVLA 구현
│   └── diffusion_agent.py
├── controllers/        # "Translator" 역할 (액션을 로봇 명령으로 변환)
│   ├── base_ctrl.py    # 추상 인터페이스
│   ├── ik_controller.py  # 현재 진행 중인 IK 방식
│   └── rola_controller.py # 추후 구현할 RoLA 방식
├── envs/               # "World" 역할 (시뮬레이션/실제 로봇 설정)
│   ├── genesis_env.py  # Genesis 환경 설정
│   └── so100_real.py   # 실제 로봇 연결 (추후 확장용)
├── utils/              # 공통 유틸리티 (좌표 변환, 로깅, 지연 시뮬레이터)
└── main_eval.py        # 실험 실행 및 데이터 수집 루프
```

### 모듈별 핵심 역할 (진행된 작업 기준)

1.  **`Agent` 모듈**:
    *   입력: 이미지 + 텍스트 명령어
    *   출력: 가공되지 않은 모델의 출력 토큰/Raw Action
    *   *장점*: OpenVLA 대신 Octo나 다른 모델로 갈아끼울 때 `main` 코드를 건드릴 필요가 없습니다.

2.  **`Controller` 모듈**:
    *   입력: 모델의 Raw Action + 현재 로봇 상태
    *   출력: 로봇 조인트 각도 (Joint Positions)
    *   *내용*: 여기에 현재 구현하신 **Action Scaling, Inverse Kinematics, Smoothing(EMA)** 로직을 넣으세요. `IKController`를 `RoLAController`로 교체하는 것만으로 실험 대조군 형성이 가능합니다.

3.  **`Environment` 모듈**:
    *   Genesis의 씬 구성, 로봇 로드, 카메라 렌더링을 담당합니다.
    *   *내용*: `evaluation.md`에서 언급된 **Sub-stepping(물리 엔진 시간 확보)** 로직은 이 모듈 내부에서 관리하여 `main` 루프를 깔끔하게 유지합니다.

4.  **`Latency Simulator` (실험의 핵심)**:
    *   `main_eval.py`에서 제어 루프 사이에 `time.sleep()`을 의도적으로 주입하거나, 비동기 큐의 크기를 조절하여 **"지연 시간 임의 조정"** 실험을 자동화할 수 있습니다.

## 3. 요약 및 다음 단계 제언

현재 진행 중인 **"OpenVLA 출력 -> IK 변환 -> Genesis 전달"**은 전체 논문 아키텍처의 가장 중요한 'Baseline'을 만드는 과정입니다.

*   **우선순위 1**: 현재의 `vla_sim.py`를 위 구조대로 **`Agent`, `Controller`, `Env`로 클래스화**하여 리팩토링하세요.
*   **우선순위 2**: 리팩토링된 환경에서 **'지연 시간 0'일 때의 성공률**을 먼저 측정하여 Baseline 데이터를 확보하세요.
*   **우선순위 3**: 이후 RoLA나 다른 제어 방식을 하나씩 추가하며 비교 실험을 진행하시면 됩니다.

이 방향으로 진행하신다면, 실용성과 학술적 깊이를 모두 잡은 훌륭한 연구가 될 것입니다. 추가로 구체적인 클래스 설계나 코드 구현이 필요하시면 언제든 말씀해 주세요!
